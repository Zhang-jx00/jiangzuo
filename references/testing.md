# 分册：测试策略

> **何时读**：写新功能要配测试、修 bug 要写回归测试、项目没测试要补、用户要求"要有测试"时。
> **前置**：摸底确认了项目的测试框架与运行方式（onboarding.md）。
> **产出**：能跑、断言有效、防回归的测试。

## 原则

- **沿用项目现状**：项目用 pytest 就 pytest，用 vitest 就 vitest，测试的目录组织、命名、fixture 写法照着现有测试抄。
- 测试是**行为的说明书**：测试名说人话（`test_order_total_includes_discount`，不是 `test_1`）。
- **先看跑得通**：接手时先跑一遍现有测试建立基线（几绿几跳几失败），新测试不能让基线变差。

## 分层与配比

| 层 | 测什么 | 数量策略 |
|---|---|---|
| 单元 | 纯函数、业务规则、边界计算 | 多：快、稳定、定位准 |
| 集成 | 接口层+数据库+服务协同 | 适中：每个核心接口至少一条 |
| E2E | 真实浏览器/完整用户路径 | 少：只保最关键的用户旅程 |

没有测试的存量项目：**不追求补齐全覆盖**，从"本次改动涉及的关键逻辑"和"修过的每个 bug"开始积累。

## 写一条好测试

1. **三段式**：准备（构造数据/状态）→ 动作（调用被测对象）→ 断言（验证结果）。
2. **断言行为，不assert实现细节**：断"返回的订单总额是 90"，不断"内部调了 discount() 方法三次"。
3. **一条测试验一件事**：失败时一眼看出什么坏了。
4. **边界清单**（每条业务逻辑过一遍）：
   - 空 / null / 缺字段
   - 0、负数、极大值
   - 超长字符串、特殊字符、emoji、多语言
   - 重复提交 / 并发
   - 无权限 / 资源不存在
   - 外部依赖失败（超时、5xx、断网）
5. **外部依赖用替身**：网络、时间、随机数、文件系统注入或 mock——测试不依赖真实第三方，也不因时区/日期飘忽不定。
6. mock 克制：mock 你不拥有的边界（HTTP、DB），**不要 mock 被测逻辑本身**——mock 掉一半业务逻辑的测试什么都没测。

## 测试先行（TDD，适用时）

修 bug 和 L2/L3 新逻辑建议先写测试：

```
写失败测试（红）→ 跑一次确认它失败 → 最小实现（绿）→ 跑确认通过 → 重构（保持绿）
```

- 修 bug 的红测试 = 复现步骤的代码化，修复后它就是防回归哨兵。
- **先写实现再补测试 = 删掉重来**（superpowers 纪律）：先跑实现心里有答案的测试没有诊断价值。

## 验证纪律

- 新增测试**必须先看到它失败**（人为制造缺陷）再看到通过——从未失败过的测试可能是恒真。
- 提交前跑**全量**测试套件，不只跑自己新写的。
- 跳过（skip）的测试必须留注释说明原因和恢复条件，不许静默堆积。

## 检查清单

- [ ] 用了项目现有框架和写法
- [ ] 每条业务规则至少一条单元测试，边界清单过了一遍
- [ ] 核心接口有集成测试
- [ ] 修过的 bug 有回归测试
- [ ] 新测试先失败后通过验证过
- [ ] 全量套件通过（基线没变差），结果贴进交付报告
- [ ] 测试里无真实密钥、无外网依赖

## 常见错误

- 测试断言"不抛异常就算过"——什么都没验证。
- mock 之后断言的是 mock 自己的调用参数，业务逻辑反而没测到。
- 依赖执行顺序或共享可变状态，单跑绿、全跑红。
- 时间相关测试用 `Date.now()`，月底月初 CI 变红。
- 追覆盖率数字写出大量断言空洞的测试——覆盖率高、信心为零。
