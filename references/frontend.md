# 分册：前端页面与交互

> **何时读**：写任何前端页面、组件、交互逻辑、前后端联调时。
> **前置**：需求已确认；视觉效果有方向（拿不准先读 ui-design.md 确认偏好）。
> **产出**：可运行的页面/组件，四态齐全，联调通过。

## 原则

**沿用优先**：项目已有组件库、请求封装、状态管理、工具函数，就用它们，先找项目里最接近的现成实现照着写。你的代码要长得像这个项目的代码。

## 可执行步骤

1. **找参照**：在项目里找一个最相似的现成页面/组件（列表页抄列表页、表单抄表单），看它怎么组织文件、命名、调接口。没有参照再按项目脚手架惯例新建。
2. **组件拆分**：
   - 一个组件一个职责；超过 ~300 行或出现第三层缩进就考虑拆。
   - 拆分信号：重复出现的 UI 块、状态+视图混杂难读、需要单独测试的逻辑。
   - props 是组件的契约：必填/可选/默认值写清楚，不传一堆布尔开关拼行为。
3. **状态管理**：
   - **服务端状态**（列表、详情）与**客户端状态**（弹窗开关、表单草稿）分开；服务端状态优先用项目现有的请求/缓存层（如 TanStack Query、Pinia store、RTK），不要手抄进 useState。
   - 状态放在需要的最小共同父级，不全局乱放。
4. **请求层**：走项目统一的请求封装（拦截器、错误处理、token 注入都在那里）；新接口不要裸写 fetch/axios。
5. **四态齐全**：每个数据视图必须有——
   - **加载态**：骨架屏或 loading，不是白屏
   - **空态**：无数据时的引导文案（"还没有订单，去下一单？"）
   - **错误态**：请求失败的重试入口，不是把异常甩用户脸上
   - **无权限态**：按项目权限规则隐藏或提示
6. **表单**：校验规则前后端一致；错误提示紧贴字段；提交中禁用按钮防重复提交。
7. **联调**：
   - 契约先行（api-design.md），先按契约 mock，再切真实接口。
   - 联调时打开网络面板核对：请求 URL/参数/头、响应结构、状态码、耗时。
   - 对不上的地方改代码**并回写契约**，不许前端偷偷适配错误字段。
8. **验证**：浏览器里实际操作每条验收标准，含边界（空列表、超长文本、断网、慢网）。控制台无新增报错和警告。

## 检查清单

- [ ] 用了项目现有组件库/封装，没有重复造轮子
- [ ] 文件命名、目录位置跟项目惯例一致
- [ ] 四态（加载/空/错误/无权限）都有处理
- [ ] 表单校验与提交防重做了
- [ ] 联调核对了请求与响应，契约已回写
- [ ] 浏览器实际点过每条验收标准 + 边界情况
- [ ] 控制台无新增报错

## 成功 / 失败示例

**好**：新列表页复用了现有 `DataTable` 组件和 `useListQuery` 封装，30 行代码完成，四态与全站一致。
**差**：引了第二个 UI 库"因为顺眼"，列表逻辑手写一遍，加载时白屏，接口报错页面直接崩。

## 常见错误

- 只测 happy path：接口 500、列表为空、文本超长时页面崩或穿帮。
- 文案、颜色、魔法数字写死在组件里，不进常量/配置。
- 状态提升到全局导致刷新全页重渲染，或本地状态该全局的不全局。
- 联调发现字段不一致，前端 `res.data?.item?.name ?? ''` 层层兜底糊过去——根因在契约，回契约修。
- 性能陷阱：大列表不虚拟化、列表项用 index 当 key、在 render 里创建新对象传给 memo 组件。
