# 分册：重构与性能优化

> **何时读**：代码变难改想整理；用户报"慢"；优化前想确认方向时。
> **前置**：项目测试可跑（onboarding.md）；性能问题有可观测手段。
> **产出**：行为不变的重构 / 有测量数据支撑的优化。

## 重构：测试保护下的小步走

重构 = **改变代码结构，不改变行为**。行为没锁住之前，禁止动手。

1. **先立保护网**：目标区域没有测试 → 先补"特征测试"（锁定当前行为，包括当前的小怪癖），或至少补核心路径测试。无保护网重构 = 盲改。
2. **小步走，每步一个意图**：一次只做一类变换——改名 / 提取函数 / 移动文件 / 合并重复 / 拆分支。禁止"重构"和"加功能"混在一个 diff 里。
3. **每步跑测试**：绿了才走下一步；红了立即回退这一步（`git stash` / 撤销），不带病前进。
4. **范围纪律**：发现更大的烂摊子 → 记录到 templates/tech-debt.md，本次不扩大战场。
5. **收尾**：全量测试 + preflight + 交付报告说明"结构改了什么、为什么、行为如何保证没变"。

## 性能优化：先测量，后动手

```
铁律：没有测量数据的优化都是瞎猜。
流程：测量 → 定位瓶颈 → 优化一个点 → 再测量对比 → 保留或回退
```

### 第一步：测量

- 定个目标口径：哪个操作、什么数据量、现在多慢、期望多快（性能预算）。
- 手段按场景选：浏览器 Performance 面板/Lighthouse（前端）、profiler（py-spy、cProfile、pprof）、慢查询日志、APM、`time` 计时最简版。
- 保留优化前的基线数字。

### 第二步：定位

按 80/20 找最大的那块，常见瓶颈排查顺序：

| 层 | 高频陷阱 |
|---|---|
| 数据库 | N+1、缺索引全表扫、一次性拉全表、大事务长连接 |
| 应用 | 循环内重复计算、串行可并行、同步阻塞外部调用、无缓存反复算 |
| 前端 | 包体积（整库引入）、重复请求、大列表不虚拟化、图片未压缩懒加载 |
| 架构 | 每请求重复建立连接、该异步的同步排长队 |

### 第三步：优化与验证

- 一次只改一个点，改完**同口径复测**，有对比数据（优化前 X ms → 优化后 Y ms）。
- 无效就回退，不为"感觉快了"保留复杂度。
- 优化不以牺牲正确性/可读性为代价：缓存要有失效策略，异步要处理失败路径，索引要评估写放大。

### 报告口径

优化类交付必须包含：基线数据 → 改动内容 → 复测数据 → 结论（达标/未达标/下一步）。只有"我做了一些优化"没有数字的报告不合格。

## 检查清单

- [ ] 重构前目标区域有测试保护
- [ ] 每个小步测试都绿
- [ ] 重构 diff 里没有功能变更
- [ ] 性能优化有优化前后的同口径数据
- [ ] 缓存/异步方案有失效与失败处理
- [ ] 未达范围的问题记入技术债
- [ ] 全量测试通过

## 常见错误

- 无测试大重构，"看起来等价"，实际上改了行为。
- 重构 PR 里夹带新功能，review 无法分开看。
- 凭直觉优化缓存/算法，测量后发现瓶颈在网络或数据库，白忙一场还引入缓存失效 bug。
- 加索引不加选择，写多读少的表被索引拖垮。
- 优化完不做回归验证，快了但错了。
