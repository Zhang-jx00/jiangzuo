# 分册：后端接口与业务逻辑

> **何时读**：实现任何后端接口、业务逻辑、定时任务、消息处理时。
> **前置**：接口契约已定（api-design.md）；数据模型已定（database.md）。
> **产出**：可调通的接口，参数校验、错误路径、日志齐全。

## 原则

**分层归属**：路由层只做协议转换（收参数、返响应），业务规则放服务层，数据访问放数据层。业务逻辑写进路由函数 = 不可测试 = 技术债。沿用项目已有分层，没有分层的小项目至少把"路由"和"业务函数"分开。

## 可执行步骤

1. **找参照**：读项目里一个同类现成接口（同资源类型、同读写模式），照它的结构写：异常怎么抛、响应怎么包、依赖怎么注入。
2. **参数校验（入口处，白名单思维）**：
   - 校验：类型、必填、长度、范围、格式、枚举合法值。
   - **白名单**：只接受已知字段，多余字段忽略或报错，不直接把请求体透传给模型（防批量赋值漏洞）。
   - 用项目已有的校验机制（Pydantic、Zod、Joi、DTO），没有就写集中校验函数，不散在业务里。
3. **业务逻辑**：
   - 一个函数一个意图；超过一屏或出现第三层嵌套就拆。
   - 业务规则用领域语言命名（`can_user_withdraw()`），不写匿名布尔表达式。
   - 跨模块调用走接口/服务，不直接摸别人的表。
4. **错误处理**：
   - 业务错误抛业务异常（带错误码），由统一异常处理器转成 api-design.md 的错误响应。
   - **禁止**：`except: pass` 吞异常；捕获后只打日志不处理不抛出；向客户端返回堆栈。
   - 外部调用（第三方 API、DB）失败要有明确的失败路径：重试（带退避）还是快速失败，超时必须设。
5. **事务与并发**：
   - 多个写操作（下单扣库存、转账）包在一个事务里，失败全回滚。
   - 并发冲突场景用乐观锁（版本号）或行锁；先想清楚"两个人同时提交会怎样"。
   - 幂等：同一请求重放不产生重复副作用（配合 api-design.md 幂等键）。
6. **日志**：
   - 关键路径有日志：入参摘要（脱敏）、结果、耗时、trace/user id。
   - 级别正确：ERROR 是需要人处理的，WARN 是可自动恢复的，INFO 是业务事件，DEBUG 是排障细节。
   - **绝不打印**：密码、token、完整身份证/手机号、密钥。
7. **性能意识（编码时顺手做，优化转 refactor-performance.md）**：循环内不发 SQL/HTTP；列表接口分页；大对象不塞会话/缓存。
8. **验证**：
   - 用 curl / .http 文件 / 项目测试实际调通：**正常请求 + 每类错误请求（缺参数、错格式、无权限、资源不存在）**。
   - 核对日志输出符合预期，无敏感信息。

## 接口完成检查清单

- [ ] 参数校验齐全（含白名单）
- [ ] 错误路径全部实现并实测过（不是只测了成功）
- [ ] 事务与并发安全想清楚（多人同时操作会怎样）
- [ ] 幂等（涉及创建/支付的）
- [ ] 日志有上下文、无敏感值
- [ ] 权限校验在服务端（security.md）
- [ ] 返回字段与契约一致，未泄露内部字段（如密码哈希、内部 id 之外的表字段）
- [ ] curl/测试实测通过，输出贴进交付报告

## 成功 / 失败示例

**好**：`POST /orders` 入口校验白名单字段 → 服务层 `create_order` 在一个事务里锁库存、建单、写流水 → 库存不足抛 `BusinessError(40020, "库存不足")` → 统一异常处理器返回标准错误结构 → 日志记录 order_id、user_id、耗时。
**差**：路由函数里 80 行：手写 SQL 字符串拼接、try 包住全部 `except Exception: return {"ok": False}`、库存检查和扣减之间没有事务（两人同时买最后一件都成功）。

## 常见错误

- `except Exception` 一把抓然后返回模糊错误——调用方和排障的人都没法活。
- 校验只在前端做，绕过页面直接打接口全放行。
- 金额用 float 参与运算。
- 返回整个 ORM 对象，把 password_hash、internal_flag 一起序列化出去。
- 定时任务没有幂等和并发保护，重复执行重复发货。
