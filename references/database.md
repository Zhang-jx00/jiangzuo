# 分册：数据库设计与变更

> **何时读**：设计表结构、改字段、写迁移、数据订正、排查慢查询时。
> **前置**：业务模型已想清（design.md）。
> **产出**：可回滚的迁移脚本、验证过的表结构、更新过的模型/文档。

## 原则

数据库变更是**最容易造成不可逆损失的操作**。三条铁律：**任何变更走迁移脚本；任何迁移可回滚；破坏性操作必须用户确认**。禁止直接在数据库里手改了事。

## 表设计

- 命名与项目现状一致（复数/单数、snake_case）；同一含义全库同名（`user_id` 在每张表里都叫这个）。
- 每表必有：主键、创建时间 `created_at`、更新时间 `updated_at`（软删除的加 `deleted_at`，前提是确认要做软删）。
- 约束在库里建实：唯一约束（防重）、外键或应用层保证的引用完整性、非空约束按业务真值定——" nullable 到处都是"是设计没想清的标志。
- 索引：为已知查询路径建（WHERE / JOIN / ORDER BY 涉及的列）；唯一索引和业务约束配套；**不为不存在查询建索引**。
- 金额用整数最小单位或 DECIMAL，不用 FLOAT/DOUBLE。
- 状态字段用有限枚举值，值域写进注释/文档。

## 变更流程（每次改表都走）

1. **确认现状**：`\d table` / `SHOW CREATE TABLE` / 读模型定义，看清现状再动手。
2. **写迁移脚本**：用项目已有的迁移工具（Alembic / Flyway / Prisma Migrate / Django migrations）；项目没有就建立约定目录 `migrations/NNN_<描述>.sql`，编号递增。
3. **每个迁移配回滚**：down 脚本或补偿 SQL。写不出回滚的变更（如删列），回滚方案就是"从备份恢复"，必须在计划里写明。
4. **评估影响**：大表加列/加索引考虑锁表与耗时（PostgreSQL 加索引用 `CONCURRENTLY`；MySQL 大表变更用 online DDL 或 pt-osc）；行数估算写进交付说明。
5. **破坏性变更清单——必须先向用户确认**：
   - DROP TABLE / DROP COLUMN / TRUNCATE
   - 不带 WHERE 或条件可能全量的 UPDATE / DELETE
   - 收紧约束（NOT NULL、唯一）可能让存量数据失败
   - 改字段类型/长度可能截断
6. **验证**：本地库跑迁移成功 → 跑回滚成功 → 再跑迁移成功；受影响的查询实际执行确认；相关测试全绿。
7. **同步**：更新 ORM 模型/实体类、表结构文档；迁移脚本随代码提交。

## 数据订正

- 订正脚本先 `SELECT` 出将影响的行数核对，再改成 UPDATE 执行——写 UPDATE 前心里有数影响多少行。
- 事务包裹，先在测试/灰度环境试跑。
- 订正前后各留一份核对数据（导出受影响行）。

## 查询健康

- 新查询在大表上 `EXPLAIN` 一眼：有没有走索引、扫了多少行。
- 报表/导出类重查询：限制时间范围、走从库或后台任务，不卡主业务。

## 检查清单

- [ ] 变更走了迁移脚本，编号/顺序正确
- [ ] 回滚脚本写过并验证过
- [ ] 破坏性操作用户确认过（有聊天记录或文档为证）
- [ ] 大表影响评估过
- [ ] ORM 模型与实际表结构一致
- [ ] EXPLAIN 看过关键查询
- [ ] 表结构文档已更新

## 常见错误

- 本地手改了表结构，忘了写迁移，别人拉代码起不来。
- 迁移写了 up 没写 down，出事时只能停机手修。
- 忘了给外键/高频 WHERE 字段建索引，上线后全表扫描。
- 软删除只删了主表，关联子表成孤儿数据。
- 在生产库直接跑未经核对的 UPDATE，影响行数超出预期。
