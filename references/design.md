# 分册：技术选型与架构设计

> **何时读**：新建项目定技术栈；给现有系统加新模块、新服务；大重构前；用户问"该怎么设计"。
> **前置**：需求已澄清（requirements.md）；摸底已做（onboarding.md）。
> **产出**：选型结论、分层与模块职责图、ADR 落盘（templates/adr.md）、用户确认过的设计方案。

## 原则

设计的原则是**够用且可演进**：先用最简单的结构满足当前明确的需求，留出变化空间，但不为想象中的未来堆抽象。每个重要取舍写成 ADR——半年后的你和接手的人会感谢这个记录。

## 可执行步骤

### 1. 约束盘点

先列出硬约束：现有技术栈（能沿用就沿用）、团队熟悉度、部署环境、性能要求、 deadline。约束优先于偏好。

### 2. 技术选型（有选型空间时）

用比较表，**至少 2 个候选**，单候选不算选型：

| 维度 | 候选 A | 候选 B |
|---|---|---|
| 与需求匹配度 | | |
| 与现有栈兼容性 | | |
| 生态与社区活跃度 | | |
| 学习成本/团队熟悉度 | | |
| 运维成本 | | |
| 主要风险 | | |

给出推荐 + 一句话理由，交用户拍板（HARD-GATE 第 4 条）。

### 3. 系统分层与模块职责

- 画出（文字图即可）分层：入口层（路由/UI）→ 业务层 → 数据层 → 外部服务。
- 每个模块用一句话定义职责，**职责说不清一句话的模块就是要拆的信号**。
- 明确依赖方向：上层可以依赖下层，反向禁止。模块间通过接口/契约通信，不偷摸摸对方的内部数据。

### 4. 关键流程与数据流

挑 1-3 个核心流程（如下单、登录），写清数据怎么流、谁写谁读哪些表/状态、失败了怎么办。

### 5. 契约与模型

- 接口契约 → 转 api-design.md，落盘 templates/api-contract.md。
- 数据模型 → 转 database.md。

### 6. 设计确认门

把方案讲给用户（大白话 + 结构图/要点列表），**确认后才进入编码**。讲的时候突出：为什么这么分、最大的风险是什么、哪块以后可能要改。

### 7. ADR 落盘

每个重大取舍（选型、分层模式、第三方服务、数据一致性方案）写一条 templates/adr.md 到 `docs/jiangzuo/adr/`。

## 项目类型适配

| 类型 | 设计注意点 |
|---|---|
| Web 全栈 | 前后端契约先行；前端状态管理选型（服务端状态与客户端状态分开）；SSR/SPA 按需求定 |
| CLI 工具 | 参数设计（`--help` 即文档）；输出给人读、`--json` 给机器读；退出码有约定 |
| 桌面/移动 | 离线与同步策略；平台差异；打包分发方式提前定 |
| 浏览器扩展 | 权限最小化；content/background 通信边界；商店审核规则 |
| 脚本/自动化 | 幂等（跑两次不出乱子）； dry-run 模式；失败可续跑 |

## 复杂度自查（过度设计警报）

出现以下情况，退一步简化：
- [ ] 为了"以后可能"的需求先建了抽象层/插件系统
- [ ] 三层包装只有一个实现
- [ ] 配置项比用户还多
- [ ] 一个简单 CRUD 被设计成事件驱动微服务

## 检查清单

- [ ] 选型有比较表和推荐理由，用户拍板过
- [ ] 每个模块一句话职责说得清
- [ ] 依赖方向没有环
- [ ] 核心流程的数据流和失败路径画过
- [ ] 接口契约、数据模型已定
- [ ] ADR 已落盘
- [ ] 用户确认过设计方案

## 常见错误

- 只给一个候选就让用户"确认"——那不是选择，是通知。
- 没约束盘点就上最爱用的技术。
- 分层画出五层但说不清每层职责。
- 设计确认门跳过——"我按最佳实践设计的"不是用户要的。
- 决策只存在于聊天记录里，代码库中无迹可寻。
