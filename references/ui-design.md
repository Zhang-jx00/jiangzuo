# 分册：UI / UX 设计

> **何时读**：做新界面、用户对"好不好看/好不好用"有要求、视觉走查、现有界面被吐槽时。
> **前置**：确认过效果偏好（见第一步）。
> **产出**：风格统一的界面 + 走查通过的记录。

## 第一步永远是：确认效果偏好（HARD-GATE）

动手前三问，给选项带推荐：

1. **风格基准**：跟项目现有页面保持一致（推荐，除非用户明说要改版）？还是有参考稿/竞品截图？（有参考图就先看图）
2. **主要设备**：桌面优先还是移动优先？两者都要的话断点怎么处理？
3. **期望档位**：能用就行（内部工具），还是需要精致（面向外部用户的产品）？

没问就自由发挥 = 返工率最高的错误。

## 设计系统先行

- **项目已有设计 token / 主题配置**（CSS 变量、tailwind.config、主题文件）：严格沿用，禁止硬编码色值和字号。
- **从零建立时**，先定 token 再写组件：
  - 色彩：主色 1、中性色阶、语义色（成功/警告/危险/链接）+ 文字三级灰（主/次/禁用）
  - 字号阶梯 4-5 档（如 12/14/16/20/24），行高配套
  - 间距用 4px 栅格（4/8/12/16/24/32），**同一页面不出现第 5 种间距**
  - 圆角、阴影各 2-3 档，足够

## 布局与层级

- 对齐是底线：同一列表的每一行、同一表单的每一栏严格对齐。
- 层级靠**字号、字重、颜色深浅、留白**表达，不靠把所有东西都加粗。
- 信息密度：工具类界面紧凑，营销类界面留白，先问清场景。
- 响应式：窄屏下不横向滚动、不重叠、不截断关键操作；表格在移动端有降级方案（卡片式或横向滚动）。

## 交互底线

- 可点击的必须**看起来**可点击（hover 有反馈、cursor 正确）；不可点击的别长得像按钮。
- 操作反馈即时：点击后 ≤100ms 有响应（loading、按钮态）；耗时操作有进度或骨架屏。
- 危险操作（删除、支付、覆盖）二次确认，文案写后果（"将删除 3 个文件，不可恢复"）而不是"确定吗？"。
- 表单：就近校验、错误具体（"手机号格式不对，应为 11 位数字"）、必填标识清晰。
- 键盘可用：Tab 顺序合理、焦点可见、回车提交表单。

## 反 AI 味清单（避免一眼假）

- [ ] 没有滥用紫蓝渐变 + 玻璃拟态堆砌
- [ ] 没有拿 emoji 当功能图标
- [ ] 图标风格统一（同一线性/同一填充，尺寸一致）
- [ ] 没有 ALL-CAPS 满屏和感叹号轰炸
- [ ] 阴影/圆角/描边全站一致，不是每个组件自己发明
- [ ] 配色克制：大面积用中性色，主色点缀，语义色只表达语义

## 设计走查清单（交付前逐项过）

- [ ] hover / active / focus / disabled 四态都设计过
- [ ] 空态、加载态、错误态有专门设计（不是白屏）
- [ ] 极端数据不破版：超长标题、0 条、9999+、负数、外文长单词
- [ ] 对比度达标：正文对背景 ≥4.5:1（大字 ≥3:1）
- [ ] 同页间距/字号/圆角属于同一套 token
- [ ] 移动端（或目标主设备）实测过
- [ ] 截图给用户确认过关键界面，再进入批量实现

## 成功 / 失败示例

**好**：先问偏好 → 用户给了竞品截图 → 提取其配色密度 → 用现有 token 实现 → 走查清单过一遍 → 截图确认。
**差**：没问偏好，AI 味紫渐变 + emoji 图标直接上线，用户："我说的是给后台人员用的，要朴素。"

## 常见错误

- 只做 happy path 的视觉，空态错误态上线时才补，风格对不上。
- 一页之内出现三种按钮圆角、两种主色。
- 走查只看 Chrome 最大窗口，不测窄屏和极端数据。
- "我觉得挺好看"代替用户确认。
