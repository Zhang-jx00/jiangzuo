# 分册：提交前审查（自审 + 互审）

> **何时读**：每次提交/交付前（必读）；用户请求审查代码；审查子代理产出的实现时。
> **前置**：改动已完成且自测过。
> **产出**：审查通过的 diff，或一份"必须修/建议修/可忽略"分级的问题清单。

## 自审心法（自己查自己有三个盲区）

- **冷却**：写完先干点别的再回来审，隔 10 分钟看的就是"别人的代码"。
- **换序**：从最危险的文件开始（改了契约/数据库/权限的），不是按修改时间顺序。
- **有罪推定**：假设这个 diff 里一定藏着一个 bug，任务就是把它找出来——扫一眼说 LGTM 不叫审查。
- **规模警觉**：单个 diff 有效变更超过 ~400 行，考虑拆分提交——大 diff 里的错误率显著更高，人也审不动。

## 流程

1. 先跑 `python scripts/preflight.py`——机器能查的（密钥、调试残留、冲突标记、TODO）不用人眼。
2. **看全量 diff**（`git diff` / `git diff --staged`），逐块过下面清单。
3. 发现的问题按严重度分级：🔴 必须修（合入会出事）／🟡 建议修（值得改但不阻塞）／⚪ 可忽略（口味问题，记录不强求）。
4. 修完 🔴 后**再跑一遍测试和 preflight**，直到干净。
5. 有子代理产出时：不轻信"已完成"汇报，用 diff 和测试输出独立核验。

## 审查清单

### 正确性
- [ ] 边界：空、0、null、单元素、超长、极值
- [ ] 错误路径：每个可能失败的调用都有处理，且处理方式正确
- [ ] 逻辑条件：`>` vs `>=`、与/或、取反、提前 return 的漏网情况
- [ ] 新代码对"不存在/为空/已删除"的数据做了假设吗？假设成立吗？

### 并发与事务
- [ ] 多个写操作在事务里，失败全回滚
- [ ] 共享可变状态的并发访问想清楚了吗（锁/原子操作/幂等）
- [ ] "两个人同时点"会怎样——重复下单、超卖、双花

### 安全（详见 security.md）
- [ ] SQL 参数化；无拼接
- [ ] 资源访问带属主校验（水平越权）；管理接口有角色校验（垂直越权）
- [ ] 无硬编码密钥/内网地址；日志无敏感值
- [ ] 用户输入到输出全程可信（注入/XSS 过一遍）

### 性能陷阱
- [ ] 循环内无 SQL/HTTP 调用（N+1）
- [ ] 列表查询有分页/上限
- [ ] 新查询在大表上走得动（EXPLAIN 看过或确认有索引）
- [ ] 无同步阻塞拖慢主流程的明显点（大文件、外部调用）

### 破坏性变更（最容易漏，专门想 2 分钟）
- [ ] 接口：删字段/改字段名/改类型/改语义——所有调用方（前端、脚本、第三方）都适配了吗？
- [ ] 数据库：迁移与存量数据兼容吗？与正在运行的旧版本代码兼容吗（滚动发布窗口期）？
- [ ] 配置：新增必填配置，没配的服务会怎样？
- [ ] 依赖升级：破坏性变更读没读过 changelog？

### 一致性与残留
- [ ] 风格与项目惯例一致（命名、目录、错误处理模式）
- [ ] 无调试残留：console.log、print、debugger、注释掉的大段代码
- [ ] 无未使用的依赖/导入/变量
- [ ] TODO 都带着上下文（谁、为什么、何时处理）
- [ ] 文案、错误信息是用户能懂的话

### 测试与文档
- [ ] 关键逻辑有测试；修过的 bug 有回归测试
- [ ] 接口变更已回写契约文档；配置变更已更新环境文档

## 结论输出格式

```
审查结论：通过 / 修复后通过 / 打回
🔴 必须修：
  1. [文件:行号] 问题描述 + 为什么必须修
🟡 建议修：
  1. [文件:行号] 建议 + 理由
⚪ 可忽略：
  ...
验证：pytest 42 passed；preflight 0 critical
```

## 常见错误

- 只读自己刚写的文件，不改调用方——编译/测试帮你抓一半，另一半靠"谁还引用它"全局搜。
- 把"测试全绿"当审查通过——测试没覆盖的破坏性变更（配置、契约、数据兼容）照样炸。
- 审查走形式：清单没逐条想，扫一眼就说 LGTM。
- 修 🔴 后不重跑验证，以为改了一行不影响其他。
