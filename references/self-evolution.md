# 分册：技能自进化（让规则被证据淘汰，而不是被遗忘）

> **何时读**：想给技能/项目"加一条规则"时；同一类问题反复出现时；复盘发现规则失效时；版本迭代前的体检。
> **前置**：有留痕可查（learnings、技术债、评测记录、git 历史）。没有留痕就没有进化，只有回忆。
> **产出**：一条经过验证的规则变更（或明确的"不改"结论）+ `docs/jiangzuo/evolution.md` 账本一行。
> **CRITICAL：读完全册再动手；步骤按顺序执行，不得跳步。**

## 先说清"自进化"是什么

不是自动改自己——那叫失控。**自进化 = 有证据就改、改了必验证、验证就退得回去。**
最危险的进化不是改错，是**只加不减**：规则越堆越多 → 常驻上下文膨胀 → 每条规则的约束力被稀释 → 技能看起来更严、实际更弱。所以本分册的一半篇幅在讲"怎么删"。

## 六道闸门（顺序不可换）

| 门 | 做什么 | 过不了怎么办 |
|---|---|---|
| ① 观测 | 跑 `python scripts/evolve_report.py .`，拿到候选清单 | 无信号就停手，别为了动而动 |
| ② 归因 | 这条候选的**根因**是什么？是规则缺失、规则没写清、还是执行者没读？ | 归因不到机制层就不要改 |
| ③ 假设 | 写一句可证伪的话：「加/改 X 之后，Y 场景会不再出现」+ 怎么算验证 | 写不出预测 = 不该改 |
| ④ 最小变异 | **一次只改一个假设**；新增 ≤40 行，且同时给出可删候选 | 想改三处 = 三个假设，分三次走 |
| ⑤ 验证 | 回归三件套（validate / unittest / preflight）+ 相关红测复跑 | 红测判别力消失 → 说明改动没生效或场景失效 |
| ⑥ 记账 | 在 `docs/jiangzuo/evolution.md` 记一行：证据 / 假设 / 变异 / 结果 / **KEEP 或 ROLLBACK** | 没记账的变更视为未发生 |

## 规则的四条生命周期出口

每条规则最终必须落在其中一个里，"不知道算不算数"不算出口：

1. **升级为硬约束**：`learnings.md` 里同一主题置信度"高"、且被 ≥2 个任务验证 → 进对应分册，并在账本记来源。
2. **保持现状**：证据不足以支撑改动，但问题真实存在 → 记账标 `WATCH`，写清下次判断依据。
3. **退役**：连续两个版本没有任何路由命中、没有任何交付引用 → 删除或降为示例。**删规则比加规则更需要勇气**：它让剩下的规则更有分量。
4. **合并**：两条规则说的是同一件事 → 合成一条，省下的行数记进账本。

## 膨胀控制（可核对的硬指标）

- 入口正文：`python scripts/validate_skill.py . --stats` 的 tokens 数。**超目标时，本次任何新增都必须配一份等量删除**，写进提交信息。
- 分册规模：接近 160 行先拆再加（`evolve_report.py` 会点名）。
- 每条新规则必须回答："**删掉这行，agent 的行为会变吗？**" 不会变 → 不提交。
- 反例配额：每加 3 条正向规则，至少配 1 条"什么时候**不要**做 X"（防技能变成永远在扩写的清单）。

## 变异安全（怎么改坏得最少）

- 改前：`git status` 干净；改后立刻提交，一条账本一行提交，`git revert` 就是回滚方案。
- **禁止**：一次提交里既改规则又改脚本又改模板却只记一个假设——回滚时会连带撤掉没问题的部分。
- 回滚条件（任一即回滚，不商量）：回归三件套变红；相关红测判别力消失；出现新的绕过口径（agent 用新规则给不合理行为背书）。
- 回滚后：账本标 `ROLLBACK` 并写清**为什么这次不成立**——失败的进化也是数据，扔掉等于白踩一次。

## 什么不能交给"自进化"

- **安全边界**：不可逆操作、密钥处理、对外发布、工作区外写入——这些只能收紧，不能因为"这次没出事"就放松。
- **用户授权**：技能可以建议，不能自作主张改用户的项目约定；改标准本身要走 ADR 并让人拍板。
- **事实**：进化只能改做法，不能改事实。查不到的就写"未验证"，不要靠改规则把没验证的说成验证过的。

## 示例

**坏的进化**：一次会话里 agent 忘了清理探针 → 于是加一条"收尾必须清理"→ 再忘了 → 加"不清理不许交付"→ 又加"preflight 必须检查"。三条规则说同一件事，入口从 5K 涨到 6K，约束力反而下降。
**好的进化**：跑 `evolve_report.py` → 观测到"高置信度教训 7 条仍留在 learnings 里" → 归因：没有从教训到分册的**升级路径**（不是没人听话，是没这条路）→ 假设：把升级动作写进 learnings 回写规则，红测 S2 的留痕项应继续通过 → 变异：改一处 6 行 → 回归全绿 → 记账 `KEEP`。

## 检查清单

- [ ] 跑过 `evolve_report.py`，候选来自证据而非印象
- [ ] 只改了一个假设，写了可证伪预测
- [ ] 新增行数与删除候选成对出现（或明确说明为何不能删）
- [ ] 回归三件套 + 相关红测复跑，结果写进账本
- [ ] `docs/jiangzuo/evolution.md` 有这一行：证据/假设/变异/结果/KEEP 或 ROLLBACK
- [ ] 变更可单独 revert（没有被夹带在其他提交里）

## 常见错误

- 把"又出问题了"当成"再加一条规则"的理由——多数时候是**上一条规则没被读到**，先查路由与措辞。
- 只记成功的进化。失败的变异不回账，下次同一个坑还会踩。
- 用进化掩盖执行问题：规则已经写了、agent 没执行，那是纪律与验证的缺口，不是规则数量缺口。
- 让报告工具替你做判断：`evolve_report.py` 给的是候选，不是结论；它看不到你的业务约束。
- 一次改多个假设，然后无法归因哪个起了作用——等于没进化，只是动了。

## 收尾红线（改完规则 ≠ 进化完成）

- 回到上文《检查清单》逐条打勾，任何一条打不了勾就把这次变异回滚。
- 账本没记 = 这次没发生；结果没跑命令 = 这次没验证。
- 入口正文变大了，必须在提交信息里写明净增数与还债计划，不许悄悄吞掉预算。
- 连续两次为同一主题加规则 → 停手，这通常是归因错了，回去重走第 ② 道闸门。
