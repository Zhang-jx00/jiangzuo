# 分册：系统化调试（修 bug）

> **何时读**：任何 bug、报错、行为与预期不符时。
> **前置**：无。
> **产出**：根因明确的修复 + 防回归测试 + 缺陷报告（templates/bug-report.md）。
> **CRITICAL：读完全册再动手；步骤按顺序执行，不得跳步。**

## 铁律

```
没有找到根因，不得动手改代码。
修完必须用原始复现步骤验证。
```

猜着改、改到好了为止、说不出为什么好了——这三种都算失败，即使现象消失了。

## 四阶段流程

### 阶段一：复现（稳定复现是前提）

- 写出**确定性复现步骤**：输入什么、点什么、期望 vs 实际。
- 不能稳定复现时先收集信息：完整报错、日志、环境（版本/OS/数据）、"上次正常到上次异常之间改了什么"（`git log`/发版记录）。
- 复现率也要记录（"100 次里 3 次"和"必现"是两种病）。

### 阶段二：定位（缩小范围）

- **读完整报错**：从第一行开始读，别只看最后一行；堆栈从自己的代码帧看起。
- **先列 3-5 个排序假设再动手验证**——只抓一个假设会锚定在第一个听起来合理的解释上。每个假设必须可证伪：说不出"如果它为真，我会看到什么"，就丢弃或改写成可证伪的形式。
- 二分缩小：注释/跳过可疑代码块、切换输入、对比正常与异常环境，每改一次只验证一个假设。
- 加日志/断点：在"正确到错误之间"的路径上埋点，跑一次，看数据在哪一步开始不对。
- 查变量：这个问题**一直都有**（只是没被发现），还是**最近才有**（找最近的变更：git log、新依赖、配置变更）？后者翻 diff。

**"在我机器上是好的"——环境差异排查清单**（本地复现不了时逐项对）：
- [ ] 依赖版本与锁文件一致？（lockfile 是否被绕过安装）
- [ ] 环境变量逐项对照（.env.example、部署平台的配置）
- [ ] 数据差异：本地库和生产库的数据量、脏数据、时区
- [ ] 时区/时钟：服务器时区、是否跨月/跨年边界、夏令时
- [ ] 网络：代理、防火墙、内网域名解析
- [ ] 运行身份：文件/目录权限、用户差异

### 阶段三：根因（问到机制层）

连问"为什么"，直到到达机制层：
> 订单金额显示错 → 为什么？取的是 `price` 字段 → 为什么取错？优惠后金额存在 `final_price`，列表接口返回了 `price` → 为什么接口返回错字段？字段映射漏改。

根因是"映射漏改"，不是"字段写错了"——前者修一处防一类，后者只修眼前这一例。

- 区分：表象（金额错）/ 直接原因（取错字段）/ 根因（映射漏改 + 没有字段级测试兜底）。

### 阶段四：最小修复 + 验证

- 只修根因，最小 diff。禁止糊表象三件套：**try-catch 吞掉报错、加个 if 绕过、把报错文案改模糊**。
- **失败熔断（≥3 规则）**：同一问题的修复尝试第 3 次仍失败 → 停止换招，回到阶段一质疑前提——复现真的可靠吗？根因假设本身错了？还是该升级给人或换方案？继续第 4 次盲试不是坚持，是沉没成本。
- 先写一个**失败测试**锁住这个 bug（testing.md），再修复，测试转绿——测试留下防回归。
- 用**原始复现步骤**完整验证；同类出现点全局搜一遍（"映射漏改"——其他接口有没有同样的漏改？）。
- 检查修复没引入新问题：跑全量相关测试。

## 缺陷报告（落盘 templates/bug-report.md）

复现步骤 / 环境与版本 / 期望 vs 实际 / 根因分析 / 修复内容与文件 / 验证证据 / 影响面（同类问题排查结果）。

## 示例

**失败的调试**："页面白屏了，可能是组件报错，我加个 try-catch 再套一层 ErrorBoundary 试试。"（没读报错、没定位、糊表象。）
**合格的调试**：
> 复现：清缓存后访问 /settings 必现白屏。控制台报 `Cannot read property 'map' of undefined (Settings.jsx:42)`。定位：`user.permissions` 未定义时直接 `.map`。根因：本次接口改造后，无权限用户该字段从 `[]` 变为不返回（后端 commit a1b2c3）。修复：前端按契约兜底为 `[]` **并**要求后端恢复字段（契约变更未同步才是根因）。已写测试锁定，复现步骤验证通过，全站搜索发现 `/profile` 页有同样隐患，一并修复。

## 常见错误

- 没复现就开始改——"我这里好的"然后永远不知道有没有修好。
- 只看报错最后一行，跳过了上面 20 行里真正的第一因。
- 同时改 3 个地方，好了也不知道是哪个起效，坏了不知道是谁弄坏。
- "修好了"但给不出根因解释——大概率是糊表象，问题会在别处再冒出来。
- 修复后不跑全量测试，按下葫芦浮起瓢。

## 收尾红线（动手完成 ≠ 可以交）

- 说"修好了"之前，必须用**原复现步骤**再跑一次并贴出输出；跑不了就是还没修好。
- 修复点必须落在根因层。只在症状处加兜底（try-catch / `?? ''`）不算修完：要么连同上游一起改，要么把"为什么只改这里"记账。
- 同一契约/同一调用形态全站搜过一遍，搜索范围与命中数写进缺陷报告；漏搜等于只修了一处。
- 回归测试要见过红再见过绿——只绿过的测试不锁行为。
- 全量测试跑完并与修复前对照，确认没有新增失败。
