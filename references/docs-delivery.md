# 分册：文档维护与交付报告

> **何时读**：每次交付前；接口/架构/配置发生变更时；长任务收尾时。
> **前置**：改动已完成并验证。
> **产出**：与代码一致的项目文档 + 交付报告（templates/delivery-report.md）。
> **CRITICAL：读完全册再动手；步骤按顺序执行，不得跳步。**

## 原则

文档不是写完代码后的装饰，是**交付物的一部分**。没更新的文档比没有文档更糟——它主动误导下一个人。发现文档与代码不符：**以代码为准，顺手修正文档**（一行也值得改）。文档更新与代码改动进**同一个 PR/提交**——分开就等于"稍后补"，永远补不上。

## 持续维护的四类文档

| 文档 | 内容 | 更新时机 |
|---|---|---|
| README / 快速启动 | 项目是什么、怎么装、怎么跑、怎么测 | 依赖/命令/环境变量变化时 |
| 架构文档 | 分层、模块职责、数据流、关键取舍（链 ADR） | 模块增删、架构调整时 |
| 接口文档 | 端点、参数、响应、错误码（或 OpenAPI 契约） | **每次接口变更立即** |
| 部署/环境说明 | 环境变量、依赖服务、发布步骤、回滚方法 | 配置/发布流程变化时 |

放在项目 `docs/` 或 README 的对应章节，跟随项目现状，不强推新结构。

## 交付报告（每个任务收尾必写）

用 templates/delivery-report.md，**四问 + 风险**，写给"下次接手的人"也能看懂：

1. **改了什么**：功能视角一句话 + 关键文件清单（含新增/修改/删除）。
2. **为什么这么改**：方案要点与被否掉的备选（一句话级别）；重要取舍链接到 ADR。
3. **怎么验证的**：实际跑过的命令与结果（测试数、检查项），不是"已自测"三个字。
4. **剩余风险与未竟事项**：没做的边界、已知小问题、建议后续动作（链技术债登记）。

轻量场景（L1 小修）可以只在对话里输出这四条，不落盘；L2/L3/L4 必须落盘到 `docs/jiangzuo/reports/`。

## 进度与交接

- 长任务（L3）每天/每阶段更新 templates/progress-report.md：完成什么、进行中、阻塞点、下一步。
- 交接/收尾时确认 `docs/jiangzuo/` 内容完整：profile、brief、plan（勾完）、ADR、契约、报告——这套档案让任何人能接手。

## learnings 回写规则

用户纠正你、或你踩了坑时，往 `docs/jiangzuo/learnings.md` 追加一行：

```
- [YYYY-MM-DD] 情境：…… 教训：……
```

- 写**可复用的行为改变**（"这家接口日期参数要传 end 排他区间"），不写情绪和流水账。
- 下次同类任务开始前，先读一遍 learnings。
- 技能层面的通用教训（所有项目都适用的）→ 建议用户沉淀回 skill 本体（提 PR 改对应分册），并经人工确认后合入。

## 检查清单

- [ ] 接口文档/契约与代码一致
- [ ] .env.example、README 快速启动仍然正确
- [ ] 重大取舍有 ADR
- [ ] 交付报告四问齐全、验证证据真实
- [ ] 剩余风险与技术债有处可查
- [ ] learnings 已回写本次教训

## 常见错误

- "文档以后统一补"——永远不会补。
- 交付报告写"已完成、已自测"六个字——没有证据、没有风险、没有文件清单。
- 接口改了字段，文档还是三个月前的——调用方照文档开发然后全线报错。
- ADR 只记"决定用了什么"不记"为什么、否掉了什么"——半年后没人敢动它。
- 交接只移交代码不移交 docs/jiangzuo/ 档案，接手的人从零摸底。
