# 任务评测（eval-first）

> 用途：官方最佳实践是"先建评测，再写技能"。本文件定义 5 个代表性任务，每个有确定的成功判据，用于：① 技能改版后回归；② 对比"有技能 vs 无技能"的实际差异；③ 发现流程在真实任务中的断点。
> 建议：每个任务分别在无技能/有技能下各跑一次，记录差异到表末。判据里所有"通过"都要求有运行证据，不接受"看起来对了"。

## 任务 1：接手陌生仓库并回答问题（L0，测 onboarding）

**准备**：任意一个 agent 不熟悉的开源仓库（建议 50-200 文件，含前后端）。
**指令**："这个仓库是怎么跑起来的？测试怎么执行？订单创建的调用链是什么？"
**通过判据**：
- [ ] 给出的启动/测试命令**实际执行**过且成功（附输出）
- [ ] 调用链标注了具体 `文件:行号`
- [ ] 项目惯例至少说出 2 条且有代码位置佐证
- [ ] 有摸底档案落盘（docs/jiangzuo/profiles/）或等价汇报结构

## 任务 2：模糊需求落地（L2，测 requirements + HARD-GATE）

**准备**：一个有列表页的最小 Web 项目。
**指令**："给列表加个筛选。"
**通过判据**：
- [ ] 第一轮响应无代码，只有 ≤3 个带推荐选项的追问
- [ ] 有大白话复述确认（理解/非目标/验收标准三段）
- [ ] 用户模拟确认后：实现四态齐全，筛选条件服务端生效（curl 验证过，不是只改了前端）
- [ ] 交付报告四问齐全

## 任务 3：带陷阱的 bug 修复（L1，测 debugging）

**准备**：在项目里埋一个"表象离根因远"的 bug：接口 A 返回 null 导致页面 B 崩，根因是上游字段改名（接口 C 的契约变了）。
**指令**："页面 B 白屏了，修一下。"
**通过判据**：
- [ ] 修复点在根因（契约同步）而非在 B 页面加 `?? ''` 糊表象
- [ ] 有先红后绿的回归测试
- [ ] 全局排查了同名契约引用（说出排查范围和结果）
- [ ] 用原复现步骤验证过

## 任务 4：数据库变更（L2，测 database + HARD-GATE）

**指令**："把订单表的 status 字段从 int 改成 string，原来的 0/1/2 变成 pending/paid/refunded。"
**通过判据**：
- [ ] 走迁移脚本且有 down 回滚，回滚实际验证过（升→降→升）
- [ ] 在改代码前就 status 语义/枚举值映射向用户确认过（HARD-GATE）
- [ ] 检查了存量数据兼容（旧值映射表）和所有读写该字段的代码
- [ ] ORM 模型、接口文档同步更新

## 任务 5：性能优化（L2，测 refactor-performance）

**准备**：列表接口在 1 万行数据下明显慢（埋 N+1 或缺索引）。
**指令**："这个接口太慢了，优化到 200ms 以内。"
**通过判据**：
- [ ] 有优化前基线数据（真实计时/EXPLAIN 输出，非估算）
- [ ] 定位到瓶颈并说明证据（不是"我觉得是 N+1"）
- [ ] 优化后有同口径对比数据，达标或说明差距原因
- [ ] 优化未改变行为（同请求同响应），全量测试通过
