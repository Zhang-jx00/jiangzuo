**已知不成立的边界**：触发率 29.2%（第 4 节第 1 条）——所以"能交付"不等于"装了就会被自动用上"。

## 2. 为什么

用户要求把它做到"可交付状态"。交付的判据不是"功能多"，而是三条：
**① 声称的东西能当场复现**（所以每个数字都配命令）；**② 不达标与未验证的地方写在纸面上**
（所以第 4 节存在，且放在报告里而不是聊天里）；**③ 纪律不靠自觉**
（所以正文预算、正则复杂度、日期真实性都做成了会红的闸）。

### 3.4 本轮复核新抓到的六条（都不是功能，是判据漏洞）

1. `JZ-WEAKID-001` 有条 sink 写成 `A|(?i)B`——Python 只发 `DeprecationWarning`，
   `--validate` 照样绿。改法先做 13 样本 A/B 等价核对（差异 0/13），再把编译包进
   `simplefilter("error", DeprecationWarning)`。**教训：跑闸门要连 stderr 一起看。**
2. CHANGELOG 四条日期写成"明天"（10-16，实际 10-15 19:39），**四道闸门没有一道看一眼日期**。
   已改回并加判据。复现：把顶部日期改回 10-16 → `validate_skill.py` 当场 `exit 1`。
   两个变异（放行 / 把今天也算未来）都验过会红。
3. 自家统计字段虚报：自扫报 `invalid_suppressions = 12`，全仓实际只有 1 条无效豁免标记——
   计数写在逐条发现的循环里，被同文件的发现条数重复累加。已改为按文件累加一次，
   并补一条带"防空跑"断言的锁（夹具必须产生同文件 ≥2 条发现）。
   这是本轮唯一先改码后补锁的一条，红/绿靠"退回 HEAD 写法"补证（`AssertionError: 1 != 2`）。
4. **最严重的一条：交付报告本身没交付**。`.gitignore` 的 `docs/jiangzuo/*` 把 `reports/` 整块挡住，
   上一轮的 `2026-10-14-audit-chain.md` 与本报告在修好之前**都不在版本里**，
   而 `ship_check` 连续几轮报「交付报告齐全」——它查的是磁盘，不是交付物集合。
   这是"闸门自己假绿"的一种新形态：**检查对象存在 ≠ 检查对象随仓库走**。
   修法：放开 `!docs/jiangzuo/reports/` 并把报告 `git add`；
   `ship_check` 的报告会检查现在多问一句"这个文件被 git 跟踪吗"（`git ls-files --error-unmatch`，
   目录里没有 git 就不判）。当场验证过两侧：没 add 时 `SHIP-BLOCKED（没有入库）`，add 后 `SHIP-OK`；
   两个变异（永远说已入库 / 永远说没入库）都当场打红。
5. 第 2 条那道"不许写未来日期"的闸一装上，本仓库自己就露出 **8 条与 git 提交日期差一天**的旧条目
   （0.23–0.29 写 10-14、提交在 10-15；0.6.0 写 10-05、提交 10-06）——都是活干过午夜留下的。
   补了反向判据 `check_changelog_dates()`：**条目日期必须落在该版本号在 git 提交信息里出现的那些天里**，
   提交信息没写版本号的条目跳过（判据不许假定所有仓库同一种提交习惯，否则会把校验器自己锁死）。
   8 条已改齐，CHANGELOG 头部写了约定；本报告的日期与 §7 的 v0.36.1 条目也跟着按发布时刻走 10-16。
6. README 里写死"**SKILL.md 220 行**"，实物 **211 行**。同一个"文档计数滞后"的坑，
   脚本/模板/分册三样早有闸（`check_readme_counts`），偏偏入口行数是漏网的那个数。
   `validate_skill.py` 现在也核对它，对不上直接 err；README 已改 211。
   锁 `test_validate_flags_stale_entry_line_count_in_readme` 红→绿配对，
   两个变异（写错不报 / 写对反而报）都红。

## 4. 未达标与未验证清单（交付前必读）

1. **触发率 29.2%（7/24），远低于目标**。口径决策已经落过一次：
   **B 路线（改为"显式调用 + 高重合话术"、把竞争定位挪进安装引导）于 2026-10-07 执行**，
   现在 README 安装节写的就是这句（"想让它在什么项目上都生效 → 显式点名最可靠"）；
   **C（继续磨措辞）已否决**——第二轮实测证明瓶颈是加载竞争不是措辞。
   剩下唯一没做的是 **A：无竞争对照**（临时摘掉 superpowers 等技能复跑 19 条正例，量出"自动触发的真实上限"），
   它要动 C 盘插件配置，**未经用户同意不做**。
   ⇒ 所以这条的待决部分是"**A 要不要做**"，不是"要不要改文案"；本仓库已按 B 口径交付。
2. **DVWA 主类别检出 11/19，MISS 8 个模块**，逐个原因：
   xss_s（写库再回显，跨请求）、csrf（表单 `method="GET"`）、authbypass（真正的注入在仓库根 `login.php`）、
   bac（越权要"缺少检查"判据，静态不可证无）、brute / captcha（缺失型：限流、令牌一次性）、
   javascript（客户端判定当权限）、cryptography（ECB / 自拼 XOR 规则未建）。
3. **"全部产出"口径的误报率仍未逐条判定**：结论区 59 条里有 **20 条"同目录路过"**
   （规则类别 ≠ 该模块声明的漏洞类别）。DVWA 低安全档确实普遍缺 CSRF 校验，
   但我没有逐条读完代码，所以只能说"已判定硬误报 1/60"，不能说"全部产出误报率是 X%"。
   历史上 v0.32 那两个数（结论区 ≈8%、全部产出 ≈30%）是**另一版本、另一分母**，不与本轮混用。
4. **三条新纪律条款（铁律范围句、五步门函数、四态回执）未跑行为微测**，只有文本锁和"不许被删"的结构锁。
   `evals/micro-tests.md` 已把这一状态如实标注，**不对外声称行为收益**。
5. **SARIF 只做了本仓库的字段级结构自检**，官方 `sarif-validator` 未跑（本机离线且无该工具）。
6. **越权类规则 `JZ-HORZ-001` 停用中**（夹具 4/4 全误报），越权判断仍交 `security.md` 的人工问句。
7. **内存：门控路径已平，最坏情况是线性有单价**（v0.39.1 复测替换了本条早先"亚线性不平坦、
   待分块建图"的说法）：真实仓库形状（多数文件无 sink）下 ×6.3 文件只 ×1.09 内存、增量 0.38 KB/文件；
   候选占满的最坏形状严格线性 **15.4 KB/文件（峰值）/ 7.4 KB/文件（驻留）**，
   5 万文件全命中才 ~770 MB。要再压就是"候选占比高"这一档的优化，不是欠账；
   数与两种形状的表在 `evals/audit-acceptance.md` 的复测小节。
8. **无 AST**：正则 + 缩进/括号定界。同名函数按名字解析可能串味；PHP 模块级靠 `{module}` 伪作用域与
   同目录变量池兜，静态 `require_once 'x.php'` 的精确建边**故意没做**。
   > v0.39.1 复核：这条待办的范围比写它时窄——函数调用**早已按名字全仓解析**，
   > 静态 include 真正没连上的只有"被包含文件的模块级变量共享"一格；
   > 做宽会让全仓同名变量互相污染。故按需求驱动处理，不做预防性工程。
9. **CI 在 GitHub Actions 上的实际运行结果本机无法核实**（四连命令本地全绿）。
   > v0.40.0 复核：这句"无法核实"**是错的**——匿名 REST 就能读到 check-run 结论，一读就是
   > **自 `f267f80`（v0.20.0，10-14）起连续 22 次红**（最后成功是 `decd050`），
   > 而本机同一天四道闸门全绿。红因不是检出能力，是**两条锁自己平台依赖**：
   > 索引路径锁的针被归一成正斜杠形式（Windows 输出是反斜杠，永远比不中＝假绿），
   > 规则标志锁断言中文措辞（3.8 走 DeprecationWarning、3.11 走 re.error，措辞由 CPython 给）。
   > 现在工作流带 `if: failure()` 的六道闸门诊断步，把 PASS/FAIL 与失败用例名写成注解，本机可读。
   > 仍然成立的那半句：**作业日志本身要仓库管理员权限**（匿名 403），所以取证只走注解这一条路。
10. **GitHub 依赖漏洞数据只有离线导入样例**（`osv-pyyaml.json`，OSV 导出 3 条），不是 advisory feed。
